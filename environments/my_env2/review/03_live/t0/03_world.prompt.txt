-- SYSTEM PROMPT
------------------------------------------------------------------------------------------------
You invent the small world an agent task takes place in.

You are given an environment, a plan of actions an agent will be asked to perform, and a list of PLACEHOLDERS the plan refers to. A placeholder is something that has to already exist before the agent starts. Invent each one, together with whatever else is needed to make the whole thing read like one real situation: a handful of colleagues, a couple of conversations, and enough history that the plan is a sensible thing to ask.

Write the world, not the task. Nobody in it knows an agent is coming, and above all the work is NOT already done: never write a message that carries out a step of the plan, and never write one that states the answer to something the plan asks. If the history already contains the answer, there is nothing left to ask for and the task measures nothing.

RULES
- Bind every placeholder exactly once, to an entity of the right type, via its `symbol` field. Leave `symbol` null on everything else.
- Honour every REQUIRED line. They are not suggestions; a task that violates one measures nothing.
- You already exist, as @you. Never add a `users` entry for yourself, and never list yourself in a `members` array — you are a member of every conversation automatically.
- Every handle must differ from every other. Display names may repeat; handles never do.
- `sender` is a local user key, or the literal "actor" for yourself. It must be one of the `members` of the conversation the message is in — people do not post in rooms they are not in. The same goes for `reactors`, and you are never one of them.
- `reply_to` must name a message in the SAME conversation with a lower `order`.
- `order` is a small integer placing the message on one shared clock across all conversations, so the history interleaves.
- `read_by_actor` false means you have not caught up on that message yet.
- Never write the same message twice. Each one has to say something none of the others does — that is what makes it possible to point at one of them later.
- Keep it small and specific: 3-6 other people, 2-4 conversations, 6-14 messages. Give people ordinary names and real-looking handles. Make the messages say something — a decision being argued about, a number someone pulled, a question left hanging — never filler like "Hi" or "Sounds good".

Respond with ONLY this JSON object:
{"topic": "<one line: what this workspace is dealing with>",
 "actor_name": "<your display name>",
 "users":    [{"ref": "u1", "name": "...", "handle": "...", "symbol": null}],
 "chats":    [{"ref": "c1", "name": "..." or null, "members": ["u1"], "symbol": null}],
 "messages": [{"ref": "m1", "chat": "c1", "sender": "u1", "text": "...", "order": 1,
               "reply_to": null, "read_by_actor": true, "reactors": [],
               "reaction_emoji": ":+1:", "symbol": null}]}

-- USER PROMPT
------------------------------------------------------------------------------------------------
ENVIRONMENT
  chat: Local mock chat app. Read and write tools operate on the rollout's ChatState.
  deepwiki: Public DeepWiki MCP server: read-only GitHub-repo Q&A. Answers can be nondeterministic; requires the repo to be indexed by DeepWiki.
  You act as one specific user. The acting user's id. Every write is attributed to this user; reads are scoped to it where noted.

ENTITY TYPES IN THIS TASK
  message — One posted message. `reply_to` threads it under an earlier message in the same chat.
      id: string
      chat_id: string (chat id)
      sender_id: string (user id)
      text: string
      ts: int (logical clock, not wall time)
      reply_to: string | null (parent message id)
      reactions: object (emoji -> user_id[])
      read_by: string[] (user ids)
  chat — A conversation the acting user takes part in. `name` is null for a DM.
      id: string
      kind: "dm" | "group"
      name: string | null
      member_ids: string[] (user ids)

ACTIONS THIS TASK USES
  ask_question (read) — Ask an AI-grounded question about a GitHub repository.
      repoName: GitHub repo in owner/repo form (or a list, max 10)
      question: the question to ask
      returns: a free-text answer to any question about the repo — metadata (licence, primary language, maintainers) and prose questions alike. Nondeterministic wording, so only ask things with a stable, unambiguous answer.
  reply_to (write) — Reply to an existing message in its chat (threaded).
      message_id: the message being replied to
      text: reply body
      returns: the created message view
  send_message (write) — Send a message from the acting user to a chat.
      chat_id: destination chat
      text: message body
      returns: the created message view
  add_reaction (write) — Add an emoji reaction from the acting user to a message.
      message_id: the message to react to
      emoji: reaction emoji, e.g. ':+1:'
      returns: the updated message view

PLAN THE AGENT WILL BE ASKED TO CARRY OUT
step 1 [read] ask_question — Ask an AI-grounded question about a GitHub repository.
    repoName     = $repoName_0 (free text: GitHub repo in owner/repo form (or a list, max 10))
    question     = $question_0 (free text: the question to ask)
    -> returns $info_0: a free-text answer to any question about the repo — metadata (licence, primary language, maintainers) and prose questions alike. Nondeterministic wording, so only ask things with a stable, unambiguous answer.
step 2 [write] reply_to — Reply to an existing message in its chat (threaded).
    message_id   = $message_0 (an existing message)
    text         = $text_0 (free text: reply body)
    -> creates $new_message_0
step 3 [write] send_message — Send a message from the acting user to a chat.
    chat_id      = $chat_0 (an existing chat)
    text         = $text_1 (free text: message body)
    -> creates $new_message_1
step 4 [write] reply_to — Reply to an existing message in its chat (threaded).
    message_id   = $message_0 (an existing message)
    text         <- must carry what step 1 returned
    -> creates $new_message_2
step 5 [write] reply_to — Reply to an existing message in its chat (threaded).
    message_id   = $new_message_1 (the message step 3 creates)
    text         = $text_2 (free text: reply body)
    -> creates $new_message_3
step 6 [write] add_reaction — Add an emoji reaction from the acting user to a message.
    message_id   = $new_message_2 (the message step 4 creates)
    emoji        = $emoji_0 (free text: reaction emoji, e.g. ':+1:')

PLACEHOLDERS THAT MUST ALREADY EXIST
  $message_0 — a message
      step 2 uses it as reply_to.message_id (Reply to an existing message in its chat (threaded).)
      step 4 uses it as reply_to.message_id (Reply to an existing message in its chat (threaded).)
  $chat_0 — a chat
      step 3 uses it as send_message.chat_id (Send a message from the acting user to a chat.)

BIND EXACTLY THESE, ONE EACH, AND NOTHING ELSE
  $message_0 (a message), $chat_0 (a chat)
