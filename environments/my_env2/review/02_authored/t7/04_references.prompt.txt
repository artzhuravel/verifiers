# Stage 4 — choose a reference mode per entity

NOTE ON FIDELITY — read this before trusting the WORKSPACE block below.

This stage ran against the CORE world, before Stage 5 padded it, and only the padded world is
shipped in the task record. The prompt below is therefore rebuilt in the right shape, with the
right blocks in the right order, but the workspace inside it is the LATER one: it contains
filler that was not present when the model actually saw this. The instructions, the block
structure and the derived lines are real; the world is a stand-in.


------------------------------------------------------------------------------------------------
-- SYSTEM PROMPT
------------------------------------------------------------------------------------------------
You decide how a task will refer to things without naming their ids.

You are given a workspace and, for each entity the task is about, the ways it could be picked out by description. Pick the ONE that suits that entity best, and say only which. What goes into it is worked out from the workspace afterwards, so you do not have to supply or check anything.

Judge it on how the finished sentence would read and on how much work it makes the reader do. Describing what someone did, or what a conversation is about, is better than restating a name or a handle — those tell the reader nothing they could not have been handed. Some modes will not fit the entity in front of you at all; say so by choosing a different one.

Respond with ONLY this JSON object, one entry per entity:
{"references": [{"symbol": "$chat_0", "mode": "<mode id>"}]}

ENVIRONMENT

ENTITY TYPES IN THIS TASK
  chat — A conversation the acting user takes part in. `name` is null for a DM.
      id: string
      kind: "dm" | "group"
      name: string | null
      member_ids: string[] (user ids)
  user — A person in the workspace. Display names may collide; handles never do.
      id: string
      name: string
      handle: string
  message — One posted message. `reply_to` threads it under an earlier message in the same chat.
      id: string
      chat_id: string (chat id)
      sender_id: string (user id)
      text: string
      ts: int (logical clock, not wall time)
      reply_to: string | null (parent message id)
      reactions: object (emoji -> user_id[])
      read_by: string[] (user ids)

ACTIONS THIS TASK USES
  list_chats (read) — List the chats the acting user is a member of.
      returns: array of {id, kind, name, members} for chats where actor is in member_ids
  read_messages (read) — Read the most recent messages in a chat, oldest to newest.
      chat_id: chat to read
      limit: max messages, most recent (optional)
      returns: array of message views {id, chat_id, from, sender_id, text, ts, reply_to, reactions, read_by}
  create_chat (write) — Create a new chat; the acting user is always included as a member.
      member_ids: user ids to include (actor added automatically)
      name: chat name; if set (or >2 members) the chat is a group, else a dm (optional)
      returns: {id, kind, name, members}
  send_message (write) — Send a message from the acting user to a chat.
      chat_id: destination chat
      text: message body
      returns: the created message view
  reply_to (write) — Reply to an existing message in its chat (threaded).
      message_id: the message being replied to
      text: reply body
      returns: the created message view
